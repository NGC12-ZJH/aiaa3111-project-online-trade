## 0. 一句话总结

v0 用关键词规则给商品分了 53 个子类，但几个大子类太粗（挂饰占 6.9%）。v1 让 LLM（DeepSeek V4 Pro）**提出**拆分方案，由人逐条**决定**，再人工修正定义和错标，得到 **76 个子类、10 个大类**，最大子类只占 3.4%。结构已冻结；下一步是让 LLM 按冻结的类别给金标准 200 个商品打标签（R1–R3），再与 A、D 的人工盲标对比，算准确率。

## 2. 方法（通俗版）

### 2.1 为什么让 LLM 提方案、由人做决定

- LLM 擅长读大量商品名，并给出"可以分成哪几类"的建议，比人工逐个翻快很多。
- 但 LLM 会犯有规律的错，比如新建一个"装饰杂物"类来装放错地方的商品，或者凭几个例子写出和实际商品矛盾的边界规则。所以**每一条建议都由人接受、修改或拒绝**，决定写进 `taxonomy_v1_decisions.json`，可以追溯。

### 2.2 v1 是怎么一步步做出来的

1. **找出要拆的子类**（第 1 步，不用 LLM）：规则提前写定。在 Discovery 期购买占比 ≥ 3.5% 或早期商品数 > 150 的要拆；出现在不到 20 个购物篮里的要合并。共找出 7 个要拆（挂饰、玩具、招牌、盘碗、小布袋、蜡烛香薰、首饰），`pet_items` 要合并，`other` 要重新归类。
2. **LLM 提方案**（第 2 步）：每个要拆的子类发一次请求，附上该子类的全部早期商品名。LLM 要按"商品是什么、怎么用"来分，**不能按颜色、图案、节日或设计系列分**，并且要说明每个商品归到哪个新子类；放错地方的商品可以直接移到已有子类。另外用 1 次请求把 `other` 里的商品重新归类，再用 1 次请求挑出"设计系列"和节日关键词。
3. **人工决定**（3 轮）：
   - 第 1 轮：7 个拆分全部接受；合并 16 组过小或重复的子类（92 → 76）；圣诞树挂饰并回"悬挂装饰"，因为节日由 `season` 属性单独表示；设计系列只保留 22 个有名字的系列（RETROSPOT、SPACEBOY……），去掉"心形""玫瑰"这类泛泛的图案。
   - 第 2 轮：修正 22 个子类的定义和边界规则。例如 v0 的 `furniture_knobs` 定义反而排除了抽屉把手，`cushions_textiles` 排除了带芯靠垫，`greeting_cards` 排除了明信片。
   - 第 3 轮：用 23 条规则纠正例子池里 61 个错标（例如 10 个咖啡杯被 v0 规则标成"茶壶"）。CHARLOTTE BAG 按 B 的决定留在"时尚手袋"。
4. **生成类别表**（第 3 步）：每个子类有英文名、中文名、一句话定义、边界规则和 3 个代表例子。例子来自不同的系列，避免"红盘、粉盘、蓝盘"这种重复；同时**避开金标准商品及其同前缀家族**，防止评测作弊。节日和设计系列用关键词匹配得到，不让 LLM 逐个判断。
5. **冻结**：记下 6 个关键文件的 SHA-256 指纹。之后第 3 步默认拒绝覆盖；打标签脚本运行前会核对指纹，文件被改过就拒绝运行。这样 R1–R6 一定用的是同一版类别。

### 2.3 LLM 打标签是怎么做的（R1–R6 共用）

每个商品发一次请求，内容分两部分：

- **固定部分（系统提示词）**：任务说明、本数据集常见缩写表（如 T-LIGHT = 茶蜡、HLDR = holder）、76 个子类的定义、边界规则和例子。这部分对所有商品都一样，DeepSeek 会把它缓存下来，重复部分按便宜很多的"缓存命中"价格计费。
- **每个商品不同的部分**：
  - 5 个"已标注的相似商品"（参考例子），用文本向量从例子池里找最相似的；如果 5 个都属于同一子类，会再补 1 个别的子类的例子，避免模型照抄；
  - 待标商品的全部写法。

模型只能回答一个 JSON：`{"l2_id": 子类代码, "confidence": 0–1, "reason": 不超过 15 个词}`。如果给的代码不在清单里，脚本会提醒它重答一次；还不行就标成 `other`，并记为 invalid。

**输入里没有销量、共购、顾客、分群或时期信息**，只有商品文字。

### 2.4 防止"评测作弊"的设计

| 风险 | 做法 |
|---|---|
| 金标准商品自己出现在参考例子里 | R1–R4 用"评测用例子库"：排除全部 200 个金标准商品，**以及与它们编码前 5 位相同的所有商品**（同系列的换色款） |
| 类别表的代表例子泄露答案 | 代表例子同样避开金标准商品及其同前缀家族 |
| 看了结果再改类别 | 结构已冻结；R1 之后如果要改，必须按 README 第 6 节的规则在**另外抽的 100 个商品**上复验 |
| 人工标注受机器标签影响 | 盲标表只有商品编码和写法，看不到 v0 或 LLM 的标签 |

## 3. R1–R3 怎么跑

### 3.1 三轮各测什么

| 轮次 | 配置 | 回答的问题 |
|---|---|---|
| **R1** | 5 个参考例子 + 主提示词 `tag_v1.txt` | 主方法在金标准上有多准？ |
| **R2** | 不给例子（k = 0），其他和 R1 一样 | 参考例子能带来多大提升？（消融实验） |
| **R3** | 5 个参考例子 + 换措辞的提示词 `tag_v1_alt.txt` | 换一种说法，结果会不会大变？（稳定性，门槛：与 R1 子类一致率 ≥ 85%） |

三轮都只标金标准的 200 个商品，例子库都是"评测用"。预设写在 `configs/taxonomy/llm_runs_v1.json`。

### 3.2 运行前的检查（只需一次）

在仓库根目录确认 key 已保存（只显示长度，不显示内容）：

```bash
awk -F= '{print $1, "length=" length($2)}' .env
```

正常输出 `DEEPSEEK_API_KEY length=35`。

### 3.3 先看提示词（dry-run，不花钱）

```bash
cd experiments/b_taxonomy
/home/zhaojinghan0204/miniconda3/envs/dsaa_ml/bin/python llm_tag.py --run R1 --dry-run
```

会打印第一个商品的完整提示词，以及大小估计（约 7,800 token 的固定部分加约 110 token 的个性化部分）。

### 3.4 正式运行

每轮一条命令，`--max-cost 3` 表示这一轮新花的钱超过 3 美元就停下：

```bash
cd experiments/b_taxonomy
/home/zhaojinghan0204/miniconda3/envs/dsaa_ml/bin/python llm_tag.py --run R1 --max-cost 3
/home/zhaojinghan0204/miniconda3/envs/dsaa_ml/bin/python llm_tag.py --run R2 --max-cost 3
/home/zhaojinghan0204/miniconda3/envs/dsaa_ml/bin/python llm_tag.py --run R3 --max-cost 3
```

- 每轮默认同时发 8 个请求，200 个商品预计 **5–15 分钟**。运行中每完成 100 个会打印一次进度。
- **中途断了怎么办**：重新运行同一条命令即可。已完成的请求从缓存读取，不会重复花钱，只补跑没完成的。
- **因为超过费用上限停下**：屏幕会显示 `Stopped early (BudgetExceeded...)`，调高 `--max-cost` 后再运行同一条命令。
- **不联网复现**：加 `--offline`，只读缓存、不调用 API。所有轮次都可以这样在任何电脑上重建结果。

### 3.5 预计费用

固定部分能否命中缓存，对费用影响很大：

| 情况 | 每个商品 | 每轮（200 个） | R1–R3 合计 |
|---|---|---|---|
| 固定部分大多命中缓存（预期） | 约 0.002–0.003 美元 | 约 0.5 美元 | **约 1.5 美元** |
| 完全没有命中缓存（最坏） | 约 0.012 美元 | 约 2.5 美元 | 约 7.5 美元 |

每轮的 `summary.json` 会给出实际的缓存命中 token 数和花费。建议先跑 R1，看实际花费和命中率，再跑 R2、R3。

### 3.6 每轮的输出怎么看

输出在 `experiments/b_taxonomy/results/llm_runs/<轮次>/`：

**`labels.csv`**：每个商品一行。

| 列 | 含义 |
|---|---|
| `stock_code`、`wording` | 商品编码和写法 |
| `l2_id`、`l1_id` | LLM 给的子类和对应大类 |
| `confidence`、`reason` | 模型自报的置信度和理由（置信度只作参考，要在金标准上校准后才能信） |
| `valid`、`note` | 输出是否合法；`retried` 表示重答过，`invalid->other` 表示两次都不合法 |
| `n_examples`、`example_l2` | 给了几个参考例子、各属于哪个子类（R2 为 0） |
| `cost`、`cache_keys`、`from_cache` | 这一条的花费、缓存记录编号、是否来自缓存 |

**`summary.json`**：本轮的汇总。

| 字段 | 含义 |
|---|---|
| `requests_done` / `requests_planned` | 完成了多少条 / 计划多少条 |
| `invalid`、`other_share` | 不合法的条数、被标成 other 的比例（门槛 ≤ 5%） |
| `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | 缓存命中和未命中的输入 token 数 |
| `reasoning_tokens` | 模型"思考"用掉的 token |
| `new_cost` | 本次新花的钱；重跑时为 0 |
| `taxonomy_sha256` | 用的是哪一版类别表，可以和冻结记录核对 |

所有原始返回都追加在 `data/taxonomy/llm_cache/llm_cache.jsonl`。里面不含 API key，可以提交。

### 3.7 跑完 R1–R3 之后

1. **不需要人工就能马上算的**：
   - R1 与 R3 的子类一致率（门槛 ≥ 85%）；
   - R1 与 R2 的差异；
   - other 占比；
   - 与 v0 标签的一致率（只作参考，v0 本身没有经过验证）。
   这一步需要一个小的比较脚本，待写。
2. **等 A、D 的盲标回来**：C 裁定分歧后形成金标准，再算各方法的子类准确率、大类准确率、宏平均 F1 和按购买量加权的准确率，同时报告两位标注人之间的一致性（Cohen's κ），分热门 100 个和长尾 100 个分别报告。
3. **按 README 第 6 节提前写定的规则选方法、决定能否冻结**：
   - 子类准确率最高的方法为主方法；
   - 达到大类 ≥ 90%、子类 ≥ 80% 才能冻结；
   - 子类在 70–80%：允许改一次，在新抽的 100 个商品上复验；
   - 子类低于 70%：主实验改用大类。
4. 达标后跑 R5（多写法稳健性）、R6（全部 4,724 个商品），冻结为正式的 `taxonomy_v1` 交给 C。R4（换模型对照）需要另一家的模型（例如学校 API 上的 gpt-5.6-luna），配置留空待定。

## 4. 注意事项

1. **价格未核实**：`configs/taxonomy/llm_v1.json` 里的价格来自第三方网站，请以 DeepSeek 平台计费页为准，核实后更新。
2. **模型会思考**：DeepSeek V4 Pro 会先"思考"再回答。打标签每条约 100 多个思考 token，影响不大；提拆分方案时每条约 2 万个，所以那一步慢且贵。
3. **温度设为 0 也不保证完全一样**：同一请求再问一次，答案可能略有不同，所以结果以缓存为准。复现时用 `--offline`。
4. **不要改已冻结的文件**：包括类别表、决定文件、例子池、定义草稿、属性表和金标准名单。确实要改，必须用 `v1_step3_build.py --unfreeze` 并重新冻结，同时作废已经跑过的 R 轮次。
5. **例子池不是金标准**：例子池（3,702 个）是 v0 规则标签加上 LLM 分配，再经过有限的人工纠正，里面仍可能有错标，评测只能以人工金标准为准。
